# 麻将助手 —— 整体架构方案

> 目标：iPad（iOS 26）上运行麻将 App，Windows 电脑实时获取牌局画面，识别场上所有**可见**的牌，
> 推算三家手牌分布 / 听牌概率 / 每张牌的放铳危险度，并给出本家打牌建议与**理由解释**，用来复盘和提升技术。

---

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| iPad 能否连电脑、在 Windows 上做助手？ | **可以。** 推荐「USB-C → HDMI + 采集卡」有线镜像，最稳定、延迟最低；备选 AirPlay 无线镜像、自研 ReplayKit 推流 App。 |
| 如何拿到场上信息？ | **画面识别（CV）为主**：从镜像画面中识别牌河、副露、宝牌指示、自己手牌。不改 App、不抓包、不注入。 |
| 核心算法 | 牌数守恒计数 → 贝叶斯/蒙特卡洛采样推断对手手牌 → 向听数 + 有效进张 + 危险度 → 攻守综合打分。 |
| Windows 技术栈 | Python（采集/识别/调度） + Rust 核心（向听、模拟，PyO3 绑定） + 本地 Web UI（第二屏/浮窗）。 |

这样「采集源」「规则」「推断模型」都可以单独替换，同一套引擎也能喂「手动录入」或「牌谱回放」。

## 3. iPad → Windows 画面获取

| 方案 | 硬件/软件 | 延迟 | 稳定性 | 备注 |
|---|---|---|---|---|
| **① HDMI 采集（推荐）** | USB-C→HDMI 转接头（iPad 需 USB-C 口）+ USB 采集卡（UVC，免驱，百元级即可） | 50–100 ms | ★★★★★ | Windows 上就是一个摄像头设备，OpenCV `VideoCapture` 直接读。画面为镜像，无需任何授权。 |
| ② AirPlay 无线镜像 | 同一局域网；Windows 装 AirPlay 接收端（UxPlay Windows 版 / AirServer 等），再对其窗口做抓屏 | 100–300 ms | ★★★ | 零硬件，但受 Wi‑Fi 影响，偶发断连。 |
| ③ 自研 ReplayKit 推流 App | 用你的开发者证书签一个 Broadcast Upload Extension，从控制中心开启「屏幕广播」，把帧压成 JPEG 经 TCP/WebSocket 推到 PC | 100–200 ms | ★★★★ | 能捕获系统级画面（含其它 App）；扩展内存上限约 50 MB，需控制帧率（2–5 fps 对回合制足够）和分辨率。 |
| ④ USB 截图（pymobiledevice3） | 数据线 + 开发者模式 + tunnel | 200–1000 ms | ★★ | 1–5 fps，仅作兜底/调试。 |

> 麻将是回合制，**2–5 fps 已够用**；高帧率主要用于捕捉「摸切 / 手切」动画（见 §6.3），属于进阶功能。

**若该麻将 App 是你自己有源码的项目**：可直接在 App 里加一个调试接口，通过 WebSocket 输出结构化牌局 JSON，
替代整个 Vision 层，精度 100%。架构上它只是另一个 `CaptureSource`，下游不变。

## 4. 视觉识别层（Vision）

### 4.1 布局标定
- 每款 App 界面布局固定。首次使用时截一张图，在标定工具里框出区域：
  `self_hand`、`self_melds`、`river[0..3]`、`melds[1..3]`、`dora_indicator`、`wall_count`、`scores`、`riichi_sticks`、`seat_wind` 等。
- 保存为 `layouts/<app名>_<分辨率>.yaml`；运行时按采集分辨率做仿射缩放。
- 牌河/对家牌是旋转的（90°/180°/270°），按区域预先旋正后再识别。

### 4.2 牌识别
- **阶段 1（快速起步）**：模板匹配 + 颜色直方图。34 种牌（+ 赤五 / 花牌）各截一张标准模板，在 ROI 内滑窗匹配。开发快，适合单一 App。
- **阶段 2（鲁棒）**：YOLOv8/11-nano 目标检测，类别 = 牌种（约 34–42 类），导出 ONNX，Windows 上用 `onnxruntime-directml`（任意显卡）推理，单帧 < 15 ms。
  - 训练数据：用标定好的区域 + 模板**自动合成**（随机缩放/遮挡/亮度/高亮框），再加少量真实截图人工校正；一个 App 几百张真实图即可收敛。
- 输出：`Detection{region, tile, confidence, bbox, rotation}`。

### 4.3 数据质量保障
- **多帧投票**：同一区域连续 N 帧（如 3 帧）一致才确认，过滤动画/特效中间态。
- **守恒校验**：任一牌种可见数 > 4 → 判定识别错误，回退并标红提示。
- **低置信度**时 UI 允许点击纠正，纠正样本自动存入训练集（主动学习闭环）。

## 5. 状态跟踪层（Tracker + GameState）

把「每帧快照」变成「牌局事件流」：

```python
class Event:            # 事件
    kind: Literal["new_round","draw","discard","chi","pon","kan","riichi","win","draw_game"]
    seat: int           # 0=自己, 1=下家, 2=对家, 3=上家
    tile: Tile | None
    tsumogiri: bool | None   # 摸切/手切（能识别时填）
    turn: int

class GameState:
    rule: RuleSet                 # 可插拔规则
    round_wind, dealer, honba, wall_remaining
    dora_indicators: list[Tile]
    my_hand: list[Tile]
    players: list[PlayerState]    # 牌河(含顺序/是否手切/是否被鸣走)、副露、立直巡目、分数
    visible_count: array[34]      # 可见牌计数（守恒核心）
```

- 以牌河**顺序追加**为主线推断事件：某家牌河多出一张 = 该家打牌；牌河尾张消失 + 某家副露增加 = 吃/碰/明杠。
- `RuleSet` 接口：是否可吃、缺一门、血战到底、番种表、宝牌、起和番等。先实现你实际在玩的那一种（见 §10 待确认）。

## 6. 分析引擎（核心）

### 6.1 可见牌计数（确定性）
`unseen[t] = 4 - visible_count[t]`，其中 unseen 分布在：三家手牌 + 牌山（含王牌）。
这是一切概率计算的基础，也是最直观的教学信息（「这张牌已经见 3 张，是绝张」）。

### 6.2 对手手牌推断（概率）
把对手手牌视为隐变量 `H_i`，用**序贯蒙特卡洛（粒子采样）**：

1. **采样**：从 unseen 牌池中，按三家已知手牌张数（13 − 3×副露数）随机发牌，得到 K 组（如 2000–5000）完整假设世界，天然满足牌数守恒。
2. **加权**：对每组假设，计算「在这副手牌下，该玩家做出观察到的舍牌序列」的似然
   `w = Π P(discard_t | hand_t, 可见信息)`。
   `P(discard | hand)` 用一个**对手行为模型**：
   - v1：基于牌效的 softmax 策略（打掉后向听数/进张越好的牌概率越高，温度参数可调）；
   - v2：用牌谱训练的神经网络策略（监督学习），更贴近真人。
   - 叠加规则特征：早巡打出的牌附近数牌持有概率下降、副露方向暗示的染手/对对、立直后摸切、宣言牌等。
3. **重采样**：每个新事件到来时增量更新权重并重采样，保持实时性（Rust 实现，单次更新 < 50 ms）。

**输出（每家）**：
- `P(持有牌 t)`：34 维热力图；
- `P(听牌)`、预估听牌巡目；
- `P(听牌 t 且和 t)` → **每张牌的放铳危险度**，以及预估打点（番数/分数）。

> 日麻类规则还可叠加现成的防守启发（现物、筋、壁、字牌生熟张），在 v1 作为先验快速可用。

### 6.3 摸切 / 手切（进阶）
手切 vs 摸切是很强的信息，但画面只能从**出牌动画起点**（手牌区中间 vs 最右侧摸牌位）判断，需要较高帧率与额外标定。列入阶段 3。

### 6.4 本家打牌建议
对手牌 14 张中每个候选打出的牌 `d` 计算：

| 指标 | 算法 |
|---|---|
| 向听数 | 查表法（预生成数牌/字牌分解表），微秒级 |
| 有效进张 | 枚举能减少向听的牌，按 `unseen` 中**非对手手中的期望剩余数**加权（用 §6.2 的推断结果，而不是简单 4−可见） |
| 和牌率 / 打点期望 | 小规模蒙特卡洛前瞻：模拟剩余巡目摸打，统计和牌率 × 番数期望 |
| 放铳风险 | Σ_i P(对手 i 听 d) × 预估失分 |
| 综合分 | `EV(d) = P(和)·得点 − P(铳)·失点 + 局势修正（点差、顺位、剩余巡目）` |

UI 给出 Top‑3 候选，每条附**自然语言理由**，例如：
> 打 **5万**：一向听，进张 6 种 18 张（↑4）；5万 已见 2 张，对家听牌率 62%，但 5万 对其危险度仅 3%（现物筋牌）。

后期可接入强化学习/监督学习模型（类似日麻 Mortal 的思路，但需按你的规则自训练），作为一个可替换的 `Policy` 实现，与规则化算法并排展示，便于对比学习。

## 7. UI 与学习功能

- **实时面板**（本地 Web，浏览器第二屏或 Tauri 置顶小窗）：
  - 本家：候选打法 Top‑3 + 理由、进张列表、向听；
  - 三家：听牌率条、34 张牌持有热力图、危险度排序（安全 → 危险）；
  - 剩余牌池计数表。
- **牌谱记录**：每局保存事件流（JSON Lines）+ 关键帧截图。
- **复盘模式**：逐巡回放，把你实际打的牌和引擎推荐对比，标出 EV 损失最大的几手 → 生成「本局错题」。
- **练习模式**：随机抽取历史局面出题「这里打哪张？」，答后展示分析。
- **手动录入模式**：线下实体牌局也能用（点选录入），同一引擎。

> 从提升技术的角度，**复盘 + 练习**比实时提示更有效：实时提示容易变成照着点，不再自己思考。建议默认「延迟显示」（出牌后再显示推荐），可切换。

## 8. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 采集 | Python + OpenCV（UVC）/ `mss`（窗口抓屏）/ asyncio TCP（ReplayKit 流） | 生态成熟 |
| 识别 | Ultralytics YOLO 训练 → ONNX → `onnxruntime-directml` | Windows 任意显卡加速，也可 CPU |
| 核心算法 | **Rust**（向听表、采样、蒙特卡洛），PyO3 暴露给 Python | 采样/模拟是热点，需要 10–100× 于纯 Python 的速度 |
| 服务 | FastAPI + WebSocket | 事件推送给 UI |
| UI | React + Vite（浏览器打开即可）；需要置顶浮窗时用 Tauri 打包 | 轻量 |
| iOS 推流（可选） | Swift，ReplayKit Broadcast Upload Extension + Network.framework | 用现有开发者证书签名 |
| 数据 | 牌谱 JSONL、标定 YAML、SQLite 存复盘统计 | 简单可迁移 |

## 9. 分阶段路线

| 阶段 | 内容 | 产出 / 验收 |
|---|---|---|
| **P0 引擎先行（1–2 周）** | 牌表示、向听/进张（Rust）、规则引擎、**手动录入** UI | 手动输入手牌即可得到牌效建议；单元测试覆盖向听表 |
| **P1 打通画面（2–3 周）** | HDMI 采集、布局标定工具、模板匹配识别、Tracker 事件流 | 能从真实对局实时生成正确的牌局状态（目标 ≥ 98% 帧级准确） |
| **P2 概率推断（2–3 周）** | 粒子采样 + 牌效行为模型、听牌率/危险度、攻守 EV、理由生成 | 三家热力图 + 危险度排序；用历史牌谱回测放铳预测 |
| **P3 学习闭环（持续）** | 牌谱记录、复盘对比、练习题；YOLO 替换模板；摸切/手切识别 | 每局错题报告 |
| **P4 模型增强（可选）** | 用积累牌谱训练对手行为网络 / 本家策略网络 | 与规则引擎对比回测提升 |

## 10. 需要你确认的问题

1. **具体规则**：国标、四川血战（缺一门/无吃）、广东推倒胡、日麻立直，还是其它？这决定 `RuleSet` 和番种/打点计算，建议先只做一种。
2. **App 来源**：是第三方 App（只能走画面识别），还是你有源码（可直接输出牌局 JSON，跳过识别层）？
3. **iPad 型号 / 接口**：是否 USB-C（决定能否走 HDMI 采集方案）？
4. **使用方式**：主要和 AI 对练 / 复盘，还是真人对局？

## 11. 合规提示

实时读取画面并给出打法，在**与真人对战的线上平台（尤其是排位或涉及真实金钱）**中通常违反平台用户协议，可能被封号，也对其他玩家不公平；
涉及金钱的麻将在国内还有法律风险。本方案按**训练工具**设计：推荐用于人机对练、牌谱复盘、练习题和线下自我分析，
并默认开启「出牌后再显示推荐」的学习模式。
